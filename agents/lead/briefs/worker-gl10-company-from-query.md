## What the operator wants (their words, 2026-11-17)
The deployment is single-user but it is a WORK system: documents live in per-company folders under source_docs (the first folder = company, stored per document) so the system knows which company a document is from.
"Just the mention of the company in the query should be enough to search for the answer." No special syntax, no per-company models, no selector: when the question names a company, the search and the answer must come only from that company's documents;
when it names several, from those; when it names none, from all (today's behaviour). This is the product's core promise and the main remaining blocker to production-readiness.

## What is true today (verified)
- The gateway `/query` already accepts `company` and `scope_query_citations` filters only the returned Sources list (app/api.py ~838-875, 1273, 1333); the answer text is generated by LightRAG from ALL companies' chunks. Open WebUI's bridge (app/api.py ~214-240) never sends a company.
- Measured on two synthetic companies (stack2 baseline, 2026-11-12): query_scope was `unscoped` on every probe; an unscoped Northwind question returned Contoso documents in its references. Scoped 27/28, cross-company 12/15, unanswerable hallucinated 8/12 (unrelated, see the M1 work).
- `COMPANY_AWARE_DEDUPE` is on in production: a file shared by two companies is indexed once, attributed to both state rows. Basenames are the only thing LightRAG stores as file_path, so attribution is a gateway-side join (state path -> company).
- The structure chunker already puts a `Doc:` header in each piece. LightRAG 1.5.7 returns references[].content as a LIST of strings (confirmed on stack2); our shared reader is app/citation_text.py.
