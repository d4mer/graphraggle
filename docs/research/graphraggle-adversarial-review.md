# GraphRAGgle adversarial review

Date: 2026-10-16. Reviewer scope: code, config, docs and briefs only (master = rc-2 at `11b1833`; worktree `graphraggle-chunking` for `transcript_prep` and loop changes). No corpus, probe, store or network access. Line numbers are for master unless prefixed `chunking:`.

## Verdict

The engineering around the pipeline (lifecycle store, CAS write-backs, dedupe rules, loop safety guards, secrets hygiene in the repo) is careful. The accuracy work built on top of it is not yet capable of finding out what helps. Three problems stack up:

1. The measuring instrument cannot see most of the effects being tested. Corpora of 2 to 6 transcripts hold roughly 16 to ~100 chunks, smaller than `chunk_top_k=20`/`top_k=40`, so every retrieval or chunking arm gets to see nearly the whole corpus. Probe sets are 24 to 40 items, one draw each, judged by the same model family that answers. The judge rubric tells the judge to ignore speaker misattribution, which is the very thing speaker-aware chunking and headers are meant to improve.
2. The "no gain" conclusions (chunk 600/2000, TOP_K, rerank, token budget) exist only as one-line assertions in briefs. No result tables are in the repo, so they cannot be audited. By the structure of the experiments they are near-certain to be saturation artefacts (see section "Conclusions we should stop trusting").
3. There is a probable structural mismatch nobody has ruled out: production chunks are 1200 tokens but the embedder reads 512. If the embedding call truncates, 58% of each chunk is invisible to vector search. If it errors or silently splits, that is a different problem. This is checkable in minutes and bears on every chunking question.

Separately, the P1 pre-processor has a real bug (a speaker whose label fails validation has their lines silently glued onto the previous speaker's turn, section 2). So P1 as built could make attribution worse while the rubric would not notice.

Recommendation: do not run more arms on the current harness. Fix the instrument first (retrieval-level metrics, a corpus larger than top_k, paired statistics, a second judge), then test the three levers in the "top 3" section.

## Notes on specific questions asked

### Why `no-recurring-speaker` can trigger wrongly (area 2)

The string is produced at `chunking: app/transcript_prep.py:489-490` when `label_lines>0`, `distinct>=2`, and no label reached `repeat_required` (3 for paren style). `label_lines` counts only lines that survive `_parse_turn`. I confirmed on synthetic text that all of these cause label lines to be dropped before counting: a comma, period (other than a single initial), `?` or `:` in the label; a nested parenthesis; a label starting with a digit; more than 4 words; a timestamp or index before the `(`; any label equal to a word in the stage-direction list (`unknown`, `speaker unknown`, `note`...). "2 labels" with 2 distinct names means the file almost certainly has hundreds of labelled lines in a shape the parser does not accept, and the 2 that passed are exceptions (for instance single-word names). The pilot's skip is therefore a parser coverage bug, not a property of the document. Two compounding facts: (a) unparsed `(Label)` lines are then glued onto the previous speaker's turn when detection does succeed (F2); (b) the 0.30 label-line density gate (`:471`) fails documents with long label-less continuation paragraphs.

### What the pilot could and could not detect

Could not: any retrieval effect (everything is retrieved, F5); attribution improvement (rubric rule 3, F4); effect on a skipped doc (F3); effect on questions whose source doc was not ingested. Could detect: gross generation breakage. So "P1 = C0" says only that headers did not change a long-context read of 16 chunks, judged leniently.

### Earlier chunk size / TOP_K / rerank / budget conclusions

Experiment definitions (`docs/ops/loop/experiments*.json`) show: E2 chunk 2000, E4 chunk 600 (E0/E1/E3 baseline, no gleaning, entity types), G1 `BRIDGE_TOP_K 80/40`, G2 no rerank, G3 total tokens 48000, G4 `20/10`. No results are in the repo ("run reports are not versioned", `docs/05`). Under the corpus size used these are all expected to be flat; see the next section.

## Top 3 accuracy levers

### 1. Make what is embedded equal what is chunked (verify, then fix)

Reason: F1. Production chunking is 1200 tokens; the embedder is 512. The research report agrees that a 512 embedder wants ~250-350-token chunks. A names-only check of the effective embedder settings costs minutes. If the embedder truncates, move chunk size to about 400 with ~50 overlap and re-ingest, which also improves entity-extraction recall per the report (section 4). Do this together with fixed transcript_prep (F2, F3) so headers sit at chunk starts of a ~400-token chunk: a header every 200 tokens inside a 400-token chunk is too dense; one header per chunk is enough. Expected effect: the largest of the three for multi-fact questions, since currently the tail of every chunk is not matched by vector search (if F1 holds).

### 2. Build an instrument that can see retrieval, then tune breadth on a real-size corpus

Reason: F4-F9, F24-F26. Concretely:
- Add a retrieval-recall metric per probe: use `only_need_context`/`include_chunk_content` to check that the evidence quote (or its key phrase) is present in the retrieved context, separately from whether the answer is right. This splits retrieval failures from synthesis failures without a judge (the earlier failure analysis, `hermes-failure-analysis-v2.md`, already classifies "retrieval_miss" vs "synthesis_wrong" by hand).
- Ingest the full set of documents plus distractors so that `chunk_top_k` is binding.
- 3 draws, paired per-question comparison, a second judge, an explicit attribution score.
- Then re-run the TOP_K/rerank/budget grid, with entity/relation tokens reduced (F10).

Without this, any lever, including 1 and 3, cannot be proven. Retrieval accuracy cannot be "as accurate as possible" if it is measured at 6 documents.

### 3. Restore whole-document context at query time, for all formats, not only transcripts

Reason: the operator's stated goal. Currently only the file path reaches the answering LLM, and nothing document-level is indexed. For a growing corpus the questions that fail first are "what was decided in the March meeting", "across the three vendor calls", and cross-document ones (0.56 at baseline). Options in order of cost:
(a) put title, date and company (from path/filename, and docx/pdf metadata) as a one-line header in the text of every document, every format (the worker already has `file_source`; extend `transcript_prep`'s metadata idea beyond `.txt`);
(b) add one document summary unit per document (10-20 lines of decisions, owners, dates; generated by the same local LLM at ingest, stored as an extra text insert with the same `file_source` stem), which answers whole-meeting questions without 20 chunks;
(c) neighbour expansion: for each retrieved chunk return the adjacent chunks or the enclosing turn range (LightRAG returns the stored chunk only, the report flags this as "check 1.5.7").
Do (a) and (b) first; both live outside LightRAG (worker side), so they do not couple to LightRAG upgrades.

Prerequisite for 1 and 3 together: fix `transcript_prep` F2/F3 and keep dedupe on original bytes (already tested).

## What I would stop doing

1. Stop running full 9-hour arms on 2-6 document corpora and judging them with 40-item single-draw comparisons. Each arm costs a night and cannot return a yes.
2. Stop spending arms on semantic/recursive chunkers (C1, C2, P2) until lever 1 is settled. The evidence in the research report is that boundary choice is a weak lever.
3. Stop maintaining or documenting as "validated" settings that the Open WebUI path never uses (F22).
4. Stop counting `refused_ok` toward the accuracy headline and stop treating a read held-out set as held-out.
5. Stop tuning with gleaning off while running gleaning on in production (F9), or change production once measured.
6. Do not enable `TRANSCRIPT_PREP_ENABLED` in production until F2, F3 and the attribution rubric are fixed.

## What I could not verify

- Whether the embedder truncates, errors or splits input beyond 512 tokens (needs the Thinkpad `.env` names and oMLX behaviour). This is the single largest unknown.
